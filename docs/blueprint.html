01Design principles

Six ideas that every other part of the system serves. Each one exists because an earlier version broke without it.

One source of instructions

All teaching rules live in one file, the faiz-teach skill. Memory notes, the insights table, commands and docs point at it and hold no rules. Seven conflicting sources caused the "inconsistent method" complaint of 14 Sep.

Evidence and instructions never mix

learning-evidence.md holds only what happened (counts, quotes, the ledger). The skill holds only what to do. Every rule cites the evidence ID or date behind it.

His words win

A rule he states changes the rulebook in the same turn, replacing the old line in place. Research loses to his record whenever they disagree.

Nothing unchecked reaches him

Every teaching part is written to a script, passes a checker, and is sent word for word. A Stop hook blocks any teaching message that is not in a validated script.

Read and judge, never write

He reads code, predicts what it does, finds planted faults and makes engineering decisions. Claude writes and runs the code he chooses (C30, 12 Sep).

Measured, not claimed

Progress bars count database rows. Builds report real output. Estimates are labelled as estimates and corrected in the open when wrong.

05The learning loops

Six loops at six speeds. The fast ones fix a single answer; the slow ones change the method itself. Each ends by writing somewhere the next loop reads.

1 · The answer loop

every answer · seconds
his answer→mark against the Key→wrong: reframe + one hint→stuck ladder→resolved

The stuck ladder is ordered by what has worked for him: first point at his own earlier answer (10 of 12, D1), then one new everyday picture (8 of 10) or a two-option question (5 of 7). Never re-explain in longer prose (0 of 5, D6). After a second failed hint, or when he asks, give the answer with a reason. A given answer returns once, reworded, in a later part.

2 · The correction loop

every complaint · same turn
his words→new C row, quoted→rulebook line replaced in place→checker updated if mechanical→commit

Examples: "explain the jargon you throw" became the glossary gate (C33); "decisions cannot be this obvious" became the trade-off check (C35); "Idw predict, just build" (C37) was superseded the same day by C39 ("I don't mind predicting if I'm given all the data"). He never has to say a thing twice.

3 · The reflect loop

every lesson close
extract Q&A from transcript→score first-try by type→ledger row + tables→rule change if 2+ parts show it→Carry-over into next script→mark reflected

extract_teaching.py pairs each question message with his reply and remembers where it stopped (reflect-state.json). SessionStart warns "UNREFLECTED TEACHING" if a session taught without reflecting. The next lesson's script is refused by the checker until it carries a Carry-over from L<n>: line, so lessons cannot forget what the last one learned.

4 · The quality pass

every 3rd lesson · or on request
teaching-researcher→graded digest, 29 sources→teaching-adapter→"replace this line / with this"→apply what his evidence supports

The researcher reads cognitive-science research (Chi, Sweller, Mayer, Roediger, Bjork, Kapur, Schwartz, Renkl) and grades each claim strong, moderate or weak. The adapter checks it against his own numbers, keeps every rule he stated, and proposes edits plus a before-and-after rewrite of a real part. The researcher re-runs when its digest is over 60 days old.

5 · The mastery loop

every lesson close
first-try accuracy per skill→faizos_analyze→mastery in DB→progress bar→teach_next gap

Mistakes are classified into an error taxonomy (errors table) that the drill command targets. The progress bar counts rows, never estimates: lessons done, production skills touched, capstone rungs backed by a real metric.

6 · The session loop

every session
SessionStart: dashboard + reflect status + cohesion check→work→Stop: session summary from DB facts, commit

The session log is written deterministically, with no model involved, so it cannot be skipped or embellished.

06The style: how a part is built

Every teaching part, including parts about real lesson files, has this anatomy. Parts built this way scored 24 of 30; parts that skipped it scored 3 of 11 on the same day (A12, A13).

The problem.
4 to 6 sentences: who uses this and why, how it works today, what goes wrong, the mechanism in physical terms, what it costs. Every rate also as counts ("92% (55 of 60)"). Banned: phrases that hide the mechanism ("happen to", "somehow").
The fix:
One sentence, plain words.
Tiny example
8 lines or fewer, generic names, only known pieces plus the one new thing.
How it works
Only for a formula or a measure: each piece on its own line, worked on one real case, then what it means for the business. Raises the size limit to 3,200 characters.
Picture:
One everyday picture that runs on the same mechanism, plus "Where it breaks".
Paths
Every path as a bullet: if this, these lines run; if that, this is skipped.
Worked chain
Before any "which way does it bend" question: wrong input → number moves → decision bends → cost, on another case. Faded once he gets one right cold.
Your turn.
Five questions (see next section).
### Key
Never sent. Each answer tagged with its question type, plus "Relies on:" listing every rule the questions use, each already taught.

Words

Plain vocabulary from his bootcamp: sticker (variable), machine (function), slot (parameter), kind, piling up. Real Python names are kept. Any word on the watchlist must be taught already or explained in the same sentence, or the checker fails the part.

One new thing per part

Count every new keyword, machine and domain word. More than one: split the part. A new measure gets one counted case from the part's own numbers.

No repetition

Never re-teach what he got right. "ik this" means move on now. No recaps of the plan, his progress or these rules. Full detail on new ideas, one line on known ones, nothing on mastered ones: the research explains why (expertise reversal).

Delivery

One part per message, then wait. Real lesson code is pasted in chat, at most 8 lines with notes; never "open the file" or "scroll to line 76" (he rejected a 300-line file unopened).

07Questions and marking

Five per part: at most one warm-up, at least three from the bank (each needs two or more steps of reasoning), exactly one "Someone broke it". He scores about 88% on plain arithmetic, so it trains nothing new.

Never

  • An answer already printed in the part (read-back check)
  • A why-question before the mechanism is shown (0 of 4 cold)
  • A table to simulate broken code (0 of 4)
  • Any hint about an answer's shape
  • Write-it-yourself or blank functions (0 of 3)

Marking

  • Right: one line naming them
  • Wrong: say so, one reframe, one hint, never partial credit plus numbers to plug in
  • "I don't understand": stop, rebuild the part with fewer new things
  • Next part only when every question is resolved

08The decision build

Every lesson ends in something real that he builds through decisions, not code (C30). Claude implements exactly his picks, even the ones the Key disagrees with, and the debrief measures the road not taken.

A decision message

One per message, 3 to 5 per build, 2,000 characters. The situation with every given stated and its source (model run, his labels, or "assumed:"); unknowns named as unknown. Each option carries:

What happensEffect on the targetCostRules out

Ends with Your pick.

What makes it hard (C35, C39)

No option rules out nothing; each wins somewhere the others lose; at least two of these are live:

a given shown as a rangeanother team's constrainta bad-month effectshared blind spotshard to undodepends on an earlier pickmeasure first

The Key names what the winner gives up and the one given that would flip the pick.

Prediction and run

BUILD-CALL lists his picks and asks for predictions with every needed number printed, at least one combining two picks. The model is written and run before Decision 1 so the givens across decisions cannot clash (they did once, in L6).

Debrief

One line per decision: his pick, what it measurably did, what the other option would have done (run when under 5 minutes, else estimated and labelled). Target missed: he changes one decision and it runs again.

10Machinery

Hooks

  • teaching-rules.sh (every prompt): injects the rulebook itself, so there is no second copy
  • teaching-guard.py (Stop): blocks unscripted teaching; fails open, never blocks twice
  • session-stop.sh (Stop): writes the session summary from DB facts and commits it
  • session-start.sh: dashboard prompt, reflect status, silent cohesion check
  • pre-tool-guard.sh (Write/Edit): the older write-from-empty guard, now off on read-and-judge tracks

Scripts

  • check_lesson_script.py: the part and decision checker; reads its markers from the rulebook
  • extract_teaching.py: pairs questions with replies; --mark records what was reflected
  • reflect_status.py: counts unreflected exchanges for SessionStart
  • check_teaching_system.py: the cohesion check
  • install-crons.sh: venture and frontier fetches, installed only with his go

Agents

  • teaching-researcher: external research, graded, cited; never edits the rulebook
  • teaching-adapter: fits the research to his evidence, proposes line-for-line edits, rewrites a real part

Both run on Opus; the reflect skill calls them (step 4b).

11Hard constraints

Never broken, whatever the request

  • Never delete, drop, rename or truncate a table, column or row; never modify existing rows in skills, mastery, missions, streak, lessons, insights or revisions. All schema changes are additive.
  • The repo is public: faiz.db stays gitignored; venture evidence stays local.
  • Tests make no network calls. TypeScript strict, no any. npm test and the smoke test pass before a commit.
  • Crontab changes and anything needing his accounts (hosting, GitHub Actions, API keys) happen only with his explicit go, done by him.
  • Writing style: plain words, no em dashes, lead with the answer.
  • Teaching rules are stored only in the rulebook: never in memory, the insights table or commands.
